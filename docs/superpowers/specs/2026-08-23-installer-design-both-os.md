# The installer, both platforms — what it installs and what it does

2026-08-23. Conceptual only; no implementation. Supersedes the installer sections of
the two earlier packaging documents, which were written before the proxy could generate
art at launch.

Shell on both sides: **bash** on Linux, **cmd/batch** on Windows. No `.exe`, no Python,
no interpreter shipped. An unsigned `.exe` is the least-trusted shape a game mod can take,
and the file that actually deserves scrutiny here is the DLL, which is unavoidable.


## 1. What the patch consists of, at rest

A patched game folder contains exactly this much of ours:

| file | where it comes from |
|---|---|
| `binkw32.dll` | **the installer copies it.** The proxy. The only code we ship. |
| `binkw32_orig.dll` | **the user's own file, moved aside.** We cannot ship Bink; it is RAD Game Tools'. |
| `tropico-fix.ini` | **the installer copies it**, once, and never again. |
| `data\*.i16` + `.i08/.i10/.i12` | **generated by the proxy at launch.** Not installed. |
| `data\ARTSET-MANIFEST.txt`, `ARTSET-STATIC.txt` | written by the proxy, so uninstall can undo it |
| `data\ARTSET-MODE.txt` | written by the proxy: which mode the art was built for |

**The installer places exactly two files.** Everything else is either the user's own file
renamed, or built by the proxy on first run. That is the whole shape of the thing, and it
is what makes a shell script sufficient on both platforms.


## 2. The shipped payload

### Windows

```
install.bat
uninstall.bat
READ-ME-FIRST.txt
tropico-patch\
  binkw32.dll
  tropico-fix.ini
  LICENSE
```

Nothing sits at the top level that could collide with a game file on extraction. The
archive extracts *into* the game folder and Windows filenames are case-insensitive, so a
top-level `binkw32.dll` would overwrite the real Bink **before any code runs** — and
`readme.txt` already exists there too.

### Linux — the same model, decided 2026-08-23

```
install.sh
uninstall.sh
play
README.md
tropico-patch/
  binkw32.dll  tropico-fix.ini  LICENSE
  tropico  tropico-common.sh  tropico-setmode.sh
  tropico-launchpoint.py  tropico-fullscreen.py
```

Extracted **into the game folder**, exactly like Windows, and acting on that folder only.
Linux filenames are case-sensitive so the collision risk is smaller than Windows', but the
same `tropico-patch/` subfolder is used for symmetry and because there is no reason for the
two platforms to be shaped differently.

Linux ships more **because it also ships a launcher**. Wine has to be told which monitor
to run on and given a virtual desktop of the right size, and the primary has to be put
back afterwards. Windows needs none of that: you start the game the way you always did.

The two Python scripts are launcher runtime, not installer: one reports which monitor the
game was launched from (without it monitor selection stops working), the other asks the
WM to fullscreen the Wine desktop.


## 3. Install — the shared core

Identical in intent on both platforms. Numbered because the order matters.

1. **Locate the game folder.**
2. **Preflight.** `Tropico.EXE` and `data\` present; our two payload files present. Checked
   by name, up front — otherwise the failure is a copy error three steps in that tells the
   user nothing.
3. **Preserve the real `binkw32.dll`.** Only when `binkw32_orig.dll` does not already
   exist, and only after confirming the file is not already ours. **§6 — this is the one
   step that can destroy something.**
4. **Install the proxy.** Copy ours over `binkw32.dll`, then verify the copy landed.
5. **Write `tropico-fix.ini` only if absent.** Never overwrite: it holds the user's
   preferences, and an upgrade that silently reset them is a worse bug than any it fixes.
6. **Delete `data\ARTSET-MODE.txt`.** This is how an install asks for fresh art: the proxy
   regenerates whenever the marker disagrees with the mode it is about to use.
7. **Remove `artsets\` if present.** Upgrade path from the staged-art versions. Only after
   step 4, so the proxy that replaces them is already in place.
8. **Report**, including that first launch spends about a second building artwork.

Steps 6 and 7 are one line each. Step 4 is a copy. The work is steps 2 and 3.


## 4. What differs, and why

| | Linux | Windows |
|---|---|---|
| finding the game | **the script's own directory.** No discovery. | the script's own directory. No discovery. |
| wrong directory | refuse, and say where it belongs | refuse, and say where it belongs |
| several installs | extract into each; each is independent | extract into each; each is independent |
| desktop entry | for **GOG only** — §4.2 | none |
| launcher | ships one, used for **GOG only** — §4.1 | none |
| `python3` | needed by the launcher | not needed at all |

### 4.1 The launcher is a GOG concern

Steam already has a launcher: Steam. Its Play button starts the game, the proxy detects
the monitor it was launched from, makes it primary, and puts it back afterwards — all
verified on the Steam edition. Nothing in `tools/tropico` is needed there.

GOG on Linux has nothing in front of the game, so the launcher earns its place: it chooses
the monitor, flips the xrandr primary, sizes the Wine virtual desktop, and restores the
primary on exit. Ship it always, use it for GOG.

Whether a folder is a Steam install is still a path test (`*steamapps*`), which works fine
per-folder.

### 4.2 The desktop entry now needs a per-install name

**A consequence worth catching before it is written.** The entry lives in
`$HOME/.local/share/applications/` and is shared, while the installer runs per folder.
That exact mismatch already produced one bug today: uninstalling a Steam install silently
removed the applications-menu entry belonging to a working GOG install.

The old fix was "remove it only when no other patched install still needs it" — which
required the discovery machinery this design deletes. So the fix has to change shape:
**name the entry after the install it points at**, e.g. `tropico-patch-<hash of path>.desktop`.
Two GOG installs then get two entries, each removed by its own uninstaller, and no script
has to know about any folder but its own.

Without this, two installs mean one entry, last writer wins, and uninstalling either takes
it away from both.


## 5. Neither installer should choose a resolution

Both currently do, and neither needs to.

* **Linux:** `tools/tropico` writes the mode into the ini on every launch, *after* the
  primary switch, because that is the only moment the display is in the state the game
  will run in.
* **Windows:** there is no launcher, so the proxy measures the display itself and picks.

So `[Resolution]` should ship **empty**, and the installer should not guess. The proxy
already treats an absent or zero width as "no override" and runs its picker.

This removes `xrandr` from the Linux installer's critical path. Keep it only as an
**advisory** preflight — telling someone their 1366x768 panel has a width this patch
cannot use is worth saying at install time, but it should not stop the install.


## 6. Uninstall — the shared core

1. **Locate.**
2. **Restore `binkw32.dll`** from `binkw32_orig.dll`, but **refuse if that backup is itself
   the proxy** — restoring it would leave a proxy forwarding to a proxy, the game would not
   start, and the uninstaller would have reported success.
3. **Leave `binkw32_orig.dll` in place.** It is the only known-good copy of the real Bink
   on disk; deleting it to look tidy means a failed copy in step 2 leaves the user with
   nothing.
4. **Delete generated art BY MANIFEST**, never by wildcard. A `del data\*.i16` would also
   take the artwork the game ships loose, which is not recoverable without reinstalling.
   Then delete the manifests.
5. **Delete `ARTSET-MODE.txt`** and `artsets\` if present.
6. **Delete `tropico-fix.ini`** and `tropico-fix.log`.
7. **Linux only:** the desktop entry and icon — but only when no other patched non-Steam
   install still needs them. They live in `$HOME` and are shared, while the script runs
   once per install.
8. **Report** that `TROPICO.CFG`, saves and `px*.PK2` were never touched.


## 7. The one step that can destroy something

Install step 3. **Never copy our proxy over `binkw32_orig.dll`** — the real Bink would be
gone for good and every movie in the game with it. It is not hypothetical: it is what a
second run of a naive installer does.

The rule is **refuse unless clearly safe**, not proceed unless clearly unsafe.

| | test | status |
|---|---|---|
| Linux | `grep -qa` for the proxy's marker string in the file | works, exercised repeatedly |
| Windows | **undecided** | see below |

On Windows the candidate is a **file-size gate**: back up only a file that is exactly
291,328 bytes, which is what `binkw32.dll` is on both the GOG and Steam editions
(byte-identical, same SHA-256 — measured, not assumed). Anything else is refused with
instructions, including a safe manual path. `findstr` for the marker can sit alongside it
as belt-and-braces, never as the only gate.

**This must be verified on real Windows before it is trusted.** It could not be verified
under Wine: Wine's `findstr` cannot search a binary at all, and its `fc /b` reports two
completely different DLLs as identical. Those are Wine reimplementations and say nothing
about Windows — but a guard against irreversible loss cannot rest on something untested.

Standing fallback while unverified: **never overwrite an existing `binkw32_orig.dll`**,
under any circumstances. Losing the backup must be impossible; being told to do one manual
step is merely annoying.


## 8. The manual path, documented

The README should say, plainly, what the installer does:

> Rename `binkw32.dll` to `binkw32_orig.dll`, then copy ours in from `tropico-patch\`.

Two reasons. It is the fallback when the installer refuses. And it is the **trust anchor**:
a cautious reader can see there is no magic, and skip the script entirely. This is also the
convention for this kind of mod — DLL fixes for old games are normally distributed as
"extract into the game folder", with no installer at all.

It sits under "If something goes wrong", so the three-line surface is unchanged:

    1. Unzip into your Tropico folder
    2. Double-click install.bat
    3. Play


## 9. Decisions taken, 2026-08-23

1. **No registry discovery on Windows.** Not worth the effort for an advisory. If
   `install.bat` is not sitting in a game folder it refuses and explains where the archive
   has to go.
2. **`install.bat` refuses rather than searches.** Simpler, and it matches the three-line
   contract: line 1 already says where to unzip.
3. **Linux adopts the same model.** Extract into the game folder; act on that folder only;
   uninstall is a local affair. This deletes `_tropico_candidates`, `tropico_find_all`,
   `tropico_find_dir`, the `libraryfolders.vdf` parsing and the per-install re-exec loop —
   about 40 of the 174 lines of `tropico-common.sh`, plus the multi-install reporting in
   the installer.

   What is given up: patching every copy on the machine in one go. That was justified by
   uninstall — removing the patch from one copy while another stayed patched, and
   reporting success. Per-folder installs make that symmetric instead: two installs mean
   the archive was extracted twice, so it is uninstalled twice, and neither script can
   make a claim about a folder it cannot see.
4. **The launcher is GOG-only in use, shipped always** (§4.1).
5. **No desktop entry for Steam installs** — already true, and now the only remaining
   platform-conditional behaviour on Linux.

### Still open

* The desktop entry's per-install naming scheme (§4.2) — the *need* is settled, the
  spelling is not.
* Whether `uninstall` should also remove the `tropico-patch/` folder and the three scripts,
  or leave them for the user to delete. Windows currently says "delete them whenever you
  like"; leaving them means re-running `install` is possible without re-extracting.
